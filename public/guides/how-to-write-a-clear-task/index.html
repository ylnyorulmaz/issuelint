PRACTICAL GUIDE / TASK QUALITY

How to write a clear task or ticket

Good task writing is not about filling in a huge template. It is about giving the next person enough information to act without inventing requirements. Here is a practical checklist, a lightweight template and examples.

01 Define the work02 Remove ambiguity03 Check before handoff
01 / THE PROBLEM

Clear is better than long.

“Improve checkout” sounds like a task. But which problem is being fixed? What should happen differently? What would count as done? A long specification can be equally hard to execute if it contains two requirements that contradict each other.

The right question is: Could a capable teammate start this work without making a material business decision for the author? If the answer is no, the task needs one more conversation or one clearer sentence.

02 / CHECKLIST

Six questions before handoff.

  1. What should change? Specify the requested action or outcome. “Make it better” is usually not enough.
  2. Where does it apply? Name the screen, workflow, system, audience or boundary when it matters.
  3. What behavior should happen? Explain relevant rules, exceptions and user interactions.
  4. How will we recognize completion? State an observable test, result or boundary. Do not invent numerical targets.
  5. What must the assignee access? Link necessary design files, documentation or approvals. Do not assume “see Figma” identifies a usable artifact.
  6. Is anything contradictory? Check dates, guarantees and exclusions. Raise an open question instead of choosing an unapproved rule.

A tiny task does not need six separate fields. The point is to identify material gaps, not to reward bureaucracy.

03 / TEMPLATE

A lightweight task template.

Start with a title and plain-text description. Add other lines only when they genuinely help the assignee.

Title: [Action + intended change]

Task: [What to change, and where]

Expected behavior: [What should happen]

Done when: [How to verify completion]

References: [Required designs or docs]

Open decisions: [Questions not yet resolved]

For a one-line button rename, the exact screen, current label, new label and “do not change behavior” may already be enough.

04 / EXAMPLES

Before and after.

Vague feature request

Before: “Add dark mode to the app.”

Clearer: “Add a theme toggle in Settings on web and mobile. If a user has not chosen a theme, use the system preference. Save an explicit selection across sessions. Check both themes on the Settings screen.”

Why: The second version defines the interaction and persistence behavior. If an existing Figma design is binding, the task should also identify how to find it.

Contradictory event rules

Before: “Deliver all webhook events in strict FIFO order. After two minutes of failures, skip the failed event and deliver newer events for the same tenant.”

Clarify: “Does FIFO still apply during failures? If skipping is permitted, is the failed event retained and retried? Can later events be delivered first?”

Why: The implementer cannot decide between conflicting requirements on behalf of the author.

A small task that is already clear

Task: “On the /settings page, rename the Save button from ‘Submit’ to ‘Save changes’. Do not change the button behavior.”

Why: Location, exact change and scope are explicit. An elaborate specification would not improve execution.
